關鍵架構決策
每一個決策背後都有 23 個 ADR（Architecture Decision Record）支撐
4B 而不是 9B
問題：RTX 3070 只有 8GB VRAM，9B 幾乎用滿，Context 只能開 8K。
決策：選 Qwopus-4B，餘裕 3.4GB 給 KV Cache，輕鬆開滿 32K。雙機跑完全相同的模型組合——任一台離線，另一台 100% 接管。
Active-Active 全對稱
問題：雙 3070 如何分工？主從模式有單點故障。
決策：雙機跑完全相同的模型組合（4B + Embed + Reranker）。任何一台離線，LiteLLM 自動剔除，其餘節點無需修改。零設定變更、零人工介入。
各司其職、互不越權
問題：LiteLLM 和 Hermes 都能做 Fallback，誰管什麼？
決策：LiteLLM 是管線工（路由、負載均衡、雲端容錯），Hermes 是決策者（跨層 Fallback、Delegation）。LiteLLM 不知道有幾台 3070，Hermes 不管負載均衡。
本地優先、雲端保底
問題：雲端 API 按量計費、資料隱私、延遲、可用性——四大痛點。
決策：本地處理 >95% 請求，雲端只作最終保底。日常使用零 API 成本。Per-turn Fallback：每一輪都先嘗試本地，失敗才跳雲端。

投資組合 DNA

為什麼需要 RAG？
幻覺風險：GPT 直接推薦可能建議不存在的或已下市的 ETF
知識截止：GPT 訓練數據有截止日期，最新 ETF 成分股可能不是即時的
精度不足：GPT 無法精確知道每一檔 ETF 的 Beta 值、夏普值
RAG 的回答
AI 不是憑空生成建議，而是先從知識庫檢索相關 ETF 數據，再基於這些真實數據生成報告。推薦的每一檔 ETF 都必須在檢索結果中存在。
單一事實來源：etf.xlsx
所有 ETF 數據的唯一來源。ChromaDB 是向量索引，etf.xlsx 是原始數據。不需處理 API 限流，不需維護爬蟲。

三層保障與防禦性回應
AI 的 JSON 輸出格式不可預測——後端是最後一道防線
三層保障
Layer 1：動態提示工程
每個使用者的偏好組合成獨一無二的 Prompt。不是固定模板，是從 DNA 動態生成的自然語言指令。
Layer 2：RAG 檢索增強
AI 推薦的每一檔 ETF 都必須在 ChromaDB 檢索結果中存在。不是憑空捏造。
Layer 3：防禦性回應轉換
GPT 的 JSON 輸出不可預測——鍵名可能中英文混雜，結構可能列表/物件切換，數值可能字串/數字不定。後端強制轉換為穩定格式。
GPT-4o 輸出的不確定性
即使使用 response_format: json_object，GPT 的輸出仍然不可控：
• 有時回傳 ETF代號，有時回傳 etf_code
• 有時 portfolio 是列表，有時是物件
• 有時 allocation 是 "30%"，有時是 30
防禦性轉換邏輯
// 鍵名統一
etf_code: item['etf_code']
　?? item['ETF代號'] ?? '',

// 結構統一
if (portfolio is Map)
　portfolio = [portfolio];
　// 單一物件轉為列表

// 型別統一
allocation: (item['allocation']
　?? item['配置比例'] ?? 0)
　.toDouble(),

// 確保前端永遠收到穩定格式
核心洞見：防禦性轉換永遠不可能覆蓋所有情況。這是所有依賴 LLM 輸出的系統的根本挑戰。

知識樹引擎：DFS + 繼承 + 標籤穿透
1,680 行的商品知識，200 行的通用演算法，零行硬編碼估價邏輯
DFS 匹配邏輯
1. keywords_not（排除優先）
「卡套」包含「卡」，但 keywords_not 排除。如果不先排除，禮物卡會誤匹配到卡套。
2. keywords（OR 匹配）
任一關鍵詞出現即匹配，繼續往深搜尋。
3. keywords_and（AND 匹配）
所有關鍵詞都出現才匹配。更精確的條件。
4. regex（正則捕捉）
捕捉面額數字。一個正則取代幾十行 if-else。
繼承與標籤穿透
屬性繼承
「星巴克隨行杯」節點沒有設 base_value → 向上找到「☕ 飲品/咖啡」的 base_value: 80。
「保健品專區」設了 0.5 倍數 → 所有子類別估值自動減半。一次改動，傳播到所有子節點。
標籤穿透
「王品」匹配到「票券」類別 → 標籤繼承 → 票券代領成本 15 元。
「不鏽鋼保溫杯」沒有標籤 → 代領成本 20 元（實物需親自領取）。
估值公式
最終估值 = max(0, int(base_value × multiplier) − receiving_cost)
視覺化編輯器
非工程師也能透過瀏覽器調整分類規則，修改後一鍵重新試算全部 CP 值，無需碰程式碼。

星級評等：閘門邏輯 vs 加權平均
有些風險是不可補償的——CP+ 5.0 但頻率 1/5 只能拿 2 星
閘門邏輯
一個閘門不通過，直接降級。不是扣分，是硬閘門。
★★★★★ 所有閘門通過
  ├ CP+ ≥ 2.0？✓
  └ 頻率 ≥ 4/5？✓

★★★★☆ 高性價比但不完美
  └ CP+ ≥ 1.0？✓

★★★☆☆ 基本合格但有風險
  └ 頻率 ≥ 3/5？

★★☆☆☆ 明確風險
★☆☆☆☆ 高風險（有零股限制等）
☆☆☆☆☆ 估值為零或數據不足
為什麼不用加權平均？
加權平均會掩蓋致命風險：
反例：CP+ 5.0 + 頻率 1/5
加權平均可能算出 3.5 分——看起來還不錯。但一支五年只發過一次紀念品的股票，風險極高。

閘門邏輯的答案：2 星。 因為頻率閘門不通過，最高只能到 3 星上限，再因低頻率降級到 2 星。
正例：CP+ 2.8 + 頻率 5/5
CP+ ≥ 2.0 ✓ 頻率 ≥ 4/5 ✓ 無風險因素 ✓
閘門邏輯的答案：5 星。
核心洞見：有些風險是不可補償的。閘門邏輯告訴使用者：「不管 CP+ 多高，低頻率就是低頻率。」
